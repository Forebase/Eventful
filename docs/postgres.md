# PostgreSQL event persistence

`PostgresPersistence` is Eventful's durable append/read backend. Install it with:

```bash
pip install 'eventful[postgres]'
```

The integration stores codec bytes rather than decomposed payload JSON. This keeps
the database boundary compatible with any `Codec` while duplicating the event type
and media type for validation and indexing.

## Setup and migrations

Pool creation and schema migration are explicit:

```python
from eventful.persistence import PostgresPersistence

store = PostgresPersistence(
    "postgresql://eventful:secret@localhost/eventful",
    table="eventful_events",
)
await store.open()
await store.migrate()
```

`open()` is lazy and idempotent. `migrate()` uses a transaction and a PostgreSQL
transaction-level advisory lock, so multiple application instances may safely race
to migrate the same table. Migrations are forward-only. Version 1 creates:

- A schema-version table tied to the configured event table.
- An append-only event table with a `BIGINT` identity position.
- Encoded event bytes, event type, codec media type, optional idempotency key, and
  database-recorded timestamp.
- A unique idempotency constraint and an event-type/position index.

The application database role needs permission to create tables and indexes during
migration. Runtime roles may instead use pre-created schema objects with only
`SELECT`, `INSERT`, and identity-sequence privileges. Eventful never performs
automatic migration from `__aenter__`; deployment tooling should call `migrate()`
deliberately.

## Append and ordered positions

```python
position = await store.append(event)
```

Positions are opaque decimal strings generated by PostgreSQL. They are globally
ordered within the configured table but may contain gaps because database identity
values are not transactional. Applications must compare/order them numerically only
if they deliberately depend on this PostgreSQL implementation; portable code should
pass positions back to the store unchanged.

## Idempotent retries

```python
position = await store.append(event, idempotency_key="request-7")
```

The first append owns the key. Retrying the byte-identical event returns its
original position. Reusing the key with a different event type, media type, or
encoded payload raises `StoreError`. Idempotency keys are table-wide and retained
indefinitely; applications should choose stable, collision-resistant keys and plan
retention before using this table as an unbounded log.

## Optimistic concurrency

```python
position = await store.append(event, expected_position=previous_position)
```

The append succeeds only when `expected_position` is the table's current maximum.
Use `"-1"` to require an empty table. A mismatch raises
`OptimisticConcurrencyError` without inserting the event.

Expected-position appends take an `EXCLUSIVE` table lock for correctness relative to
ordinary inserts. This is a global-stream concurrency check and can reduce write
throughput. Per-aggregate stream concurrency requires a future stream identifier and
schema revision rather than this table-wide mechanism.

## Replay snapshots

```python
async for event in store.read(after=position):
    ...
```

`after` is exclusive. A read holds a pooled connection and a read-only,
repeatable-read transaction until the iterator ends or is closed. Rows stream in
bounded batches (`read_batch_size=500` by default), so appends committed after the
snapshot begins are not included and large logs are not loaded into memory at once.

Always exhaust or explicitly close abandoned async iterators so their transaction
and pool connection are returned promptly.

Stored media types and duplicated event types are validated during replay. Corrupt,
unsupported, or undecodable rows raise `StoreError` rather than being silently
skipped.

## Lifecycle and ownership

- URL-created pools are owned and closed by the store.
- A `pool=` supplied by the caller is never closed by the store.
- `close()` is asynchronous and idempotent, and later operations fail.
- Async context management opens and closes the pool but intentionally does not
  migrate the schema.
- Cancellation is preserved; connection and transaction context managers perform
  cleanup before it escapes.

## Reliability boundary

Successful append means PostgreSQL committed the row under the database's configured
durability settings. Eventful does not configure PostgreSQL replication,
`synchronous_commit`, backups, point-in-time recovery, encryption, authentication,
row-level security, retention, or disaster recovery. Those remain deployment
responsibilities.
